# 蓝牙操作中断与反复重连：针对 2.13 网页版的改进

2026-10-18。用户明确反馈：能够连接，但操作时容易断开或反复重连。本文基于当前源码、既有实际任务记录、GCLab APK/固件静态证据和官方 BLE 客户端文档。未修改运行程序、固件或蓝牙适配器，未连接实物。

最值得先改的是连接生命周期和恢复策略。网页是界面，实际蓝牙由 Windows 后台 Bleak/WinRT 执行；改进应落在后台会话管理、任务阶段和连接状态反馈。当前没有证据需要更换网页架构。

## 已找到的直接证据

| 证据 | 当前行为 | 对体验的影响 |
|---|---|---|
| `gateway.py:280` 和 `:423` | 每次任务新建客户端并连接，finally 无条件断开；每个新连接强制重新发现服务 | 连续读取、设置、校时或切页都会反复建立会话，正常断开与故障容易混在一起 |
| `gateway.py:294–295` | 每次任务重新读取能力与电压 | 操作链有重复初始化成本；其中实时状态和发图电压不能为了省时间随意变成陈旧缓存 |
| `gateway.py:458–460` | 连接/超时失败约10–18秒后重试，最多持续24小时 | 后台预约可以等待，用户正在点击操作时则会感觉无休止重连 |
| `app.js:6` | 所有 waiting 任务统一显示“等待接收窗口” | GATT不可达或连接故障也可能被显示成正常省电窗口，解释不准确 |
| 客户端构造没有 disconnected_callback | 没有主动/意外断开的独立事件处理 | 缺少能解释掉线阶段的状态，往往等到下一次I/O报错才察觉 |
| `gateway.py:18/:270`、`server.py:42` | 扫描和任务持同一锁；同步扫描API最多等12秒 | 长任务占锁时扫描会超时；不能把它误报成设备没有广播 |

上述属于当前源码可确认行为，不等于已证明每次真实意外断开的无线原因。短连接本身是一种省电取舍；问题是它不适合直接承担连续交互体验，且页面没有解释连接正常释放的状态。

## 可以从 GCLab 学到什么

App 的 `_connectToDevice`、`_handleDeviceNotify`、`_reconnect`、`setNotifyValue`、订阅通知失败提示，以及等待设备配置/MTU的提示，支持它有集中连接、通知处理和重连的实现线索。固件还有MTU、忙状态、OTA互斥与断开清理路径。

值得借鉴的原则是：连接建立后先完成初始化，连接状态通过事件明确更新，业务操作在已就绪会话中执行。**本次没有恢复完整Dart调用链，不能宣称已证明GCLab采用某个具体保活时长或重试算法。**下面的短时连接复用是针对本项目提出的设计。

本机2.13开发环境实际为 Python3.12.7、Bleak3.0.2；其官方API提供 `disconnected_callback`。WinRT的 `use_cached_services=False` 会强制从远端读取服务；Windows创建对象不等于已经完成可用连接，服务发现及读写也可能触发连接。[Bleak客户端文档](https://bleak.readthedocs.io/en/latest/api/client.html)、[WinRT缓存参数](https://bleak.readthedocs.io/en/develop/_modules/bleak/args/winrt.html)、[Microsoft GATT客户端文档](https://learn.microsoft.com/en-us/windows/uwp/devices-sensors/gatt-client)

## P0：交互时短时复用同一个连接

对同一块屏连续操作，使用“连接并初始化一次 → 顺序执行操作 → 空闲后释放”。首轮以20秒空闲租期作为待测候选，不把它写成实测最佳值。传图、刷新确认和OTA期间不因空闲租期到期而断开。

实现约束：

1. 首轮只维护一个活动设备会话，继续串行GATT操作，不同时给多块屏建立连接。已有任务/适配器互斥不能为追求速度直接去掉。
2. 新连接仍发现服务、验证设备身份与能力；同一连接内可复用服务和能力。每个业务动作仍读取必要的当前状态，发图电压按现有正确性要求读取。
3. 成功任务结束后延迟释放会话；用户切换设备、显式断开、空闲超时或程序退出时释放。扫描请求需明确协调正在使用的会话，不能抢占已提交的任务。
4. OTA重启后必须废弃旧会话与发现对象，重新发现、读新固件ID，不复用旧服务或能力。
5. 不自动开启永久保活、绑定/配对或后台高频心跳。后台定时任务可继续使用短连接；连续交互和无人值守分别取舍。

需要修改的关联点：Gateway客户端生命周期、worker空闲时释放、App退出清理、扫描互斥、OTA重启路径与现有传输测试。不是只删除finally中的disconnect；那样会留下无法管理的会话。

预期收益是减少正常操作间不必要的重连和服务发现。它可能改善Windows反复建链带来的失败机会，但无法单独修复射频、电源或适配器驱动问题；空闲连接会增加连接占用和耗电，须实测。

## P0：分清断开原因与恢复状态

引入准确的实时连接状态：未连接、正在连接、初始化、可操作、发送中、刷新中、正常释放、意外断开、恢复等待、恢复失败。`最近画面`及固件最后记录继续保留，但不充当实时在线证明。

disconnected_callback仅登记事件及失效会话；业务事务负责决定停止、重试或结果未知。主动释放前标记原因，区分空闲超时、切设备、退出与OTA预期重启，防止断开回调误触发自动重连。

把任务waiting原因分成：设备尚未广播/接收窗口、等待蓝牙通道、建立连接失败、GATT不可达。显示尝试次数和下次恢复时间。Windows `Unreachable` 的官方含义是此时无法与设备通信，不直接证明标签已关闭蓝牙或停止广播。[Microsoft状态定义](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattcommunicationstatus?view=winrt-28000)

## P1：交互恢复应有边界

交互操作可评估至多2次短时恢复，例如约1秒、3秒并带小幅抖动；次数及总时长通过实机测试确定。后台预约依然可以等待下一接收窗口，不能把24小时等待策略直接呈现为用户点击后的唯一行为。

连续恢复失败后停止密集循环，给出具体阶段、错误与手动重连入口；重新扫描取得新设备对象。不要自动重启系统蓝牙、重配对、刷固件或无限重复同一连接请求。

错误处理必须按事务阶段：

| 阶段 | 恢复原则 |
|---|---|
| 扫描/建链/只读查询 | 有界重试，旧会话失效后重新发现 |
| 传图未提交 | 中止或按协议安全重启传输，保持偏移/校验验证 |
| 显示命令已可能接受或已提交 | 记录未知结果；连接恢复后按transfer_id/显示代次核对，不盲目再刷 |
| 提醒已提交 | 使用现有token/CRC/槽信息核对，避免生成第二条提醒 |
| OTA已提交重启 | 重新发现并核对新固件ID，不再次擦写 |

不能把所有 `BleakError/OSError` 都转换为自动重试；它可能发生在设备已经接受显示或提交操作之后。现有 `DeliveryUnknown` 及双区OTA最后提交规则必须保留。

## P1：减少无效交互，随后再改固件性能

在状态已经读取并一致时，评估跳过相同的策略重复设置，仍保留必要读回。普通probe可把深度槽位/像素核对与轻量连接确认区分，避免用户只想确认可操作却触发长时间完整像素读取。

下一步再合入WI-5的大包传图，降低471个小包的连接占用。普通图像的新包长必须由固件能力声明；保留带响应写入、顺序偏移、校验和及BUSY/代次完成检查。不是先把写入改成无响应就能获得可靠连接。

若上述改动后仍有真实掉线，再针对固件的连接间隔、从机延迟、监督超时、刷新期间调度和电源进行单变量排查。当前没有这几项的实时读回与抓包证据，不直接套用另一芯片的参数或再次猜测广播间隔。

## 验收应证明体验变化

- 同一块屏连续执行读取、设置、校时和切页：租期内只建立一次连接；空闲后正常释放；下一次操作可恢复。
- 真实意外断开能立即更新状态，明确发生阶段；预期断开不启动重连循环。
- 设备切换、OTA重启、扫描竞争与程序退出后没有遗留会话。
- 提交后断线不重复发图、不重复提醒、不重复OTA；旧设备仍可使用。
- 同一台电脑、同一适配器与同一块标签对照：首次就绪耗时、连续20次操作的重连数和意外失败数、传图时间与恢复次数；时间与计数同时记录。
- 连续交互与空闲释放分别测电流；GATT完成和BUSY结束不等于光学验收。

本轮结论：当前“每操作一次就断开再连接”是直接可改的交互策略；历史GATT恢复循环则要求有界、按阶段处理。优先完成这两项，比先调整广播间隔更贴近用户反馈。尚未修改生产代码或发布新包，也未声称真实掉线根因已全部定位。
