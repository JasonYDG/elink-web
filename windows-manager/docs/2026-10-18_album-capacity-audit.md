## 4.2固件的实际结构

| 原BIN函数/指令 | 实际行为 |
|---|---|
| `0x426DAC`，尤其`0x426DD0..0x426DF0` | 按型号算图像长度，向上对齐4096B，以`0xB6000`除以槽长，最大45槽 |
| `0x425D46..0x425D4C`、`0x426D82..0x426D8C` | 图片地址为`0x41000 + 槽号 × 槽长 + 读取偏移` |
| `0x42AC1C` | 元数据保存地址`0x40000`，槽记录位于`0x40100`，备注位于`0x40400`；34B总头、每槽16B记录、64B备注 |
| `0x425FA8` | 结束上传时记录长度、CRC、有效状态，调用元数据保存 |
| `0x427018` | 保存轮播模式、间隔和7项映射；模式0停止定时器 |
| `0x42594C`、`0x4114A4` | 注册参数60000的回调；回调加60并置事件标志，符合分钟节拍，真实时长未实测 |
| `0x425894`、`0x422354` | 间隔模式比较经过时间与间隔×60；顺序寻找有效槽，循环回绕；另有星期映射模式 |
| `0x41FDE6..0x41FE06` | 主事件流程取下一槽，进入显示函数`0x425D10` |
| `0x42FBC0..0x42FC4E` | 能直接映射时使用映射指针，否则最多244B一块读取并调用屏幕发送回调；无需同时缓存所有图片 |

因此，原固件使用的是**像素槽位 + 持久播放配置 + 定时选槽 + 分块读出显示**。这条路径不需要手机持续发送，也没有在这条已核对路径中看到JPEG解码。不能据此概括整个固件是否支持其他格式。

`0xB6000 = 745472B = 728KiB`，内部图库预算地址为`[0x41000,0xF7000)`，已经超过2.13的整颗512KiB容量。以普通400×300双色位平面30000B算，32KiB对齐后是22槽，不是所有屏都45张。此处证明的是该BIN的布局算法和地址预算，未证明当前4.2设备实际容量或这些地址均写入成功。

原BIN代码映射`[0x404000,0x43E3C4)`，入口`0x4040E0`；2.13当前应用装载到`0x07FC0000`的系统RAM，SDK也明确把外部程序的代码区放在SRAM。不能把4.2地址或机器码直接搬到2.13。

### 对现有2.13字库的无损体积实验

没有删字、改字号或更改画面。对当前四张应用字库共215个字形保留原索引和5B度量信息，分别测量去掉每行字节填充、以及简单的0/1游程编码。每个字形在64组游程参数下均解码并逐像素比对原始点阵，通过后选择各表最小值。脚本为`backup/2026-10-18/album-capacity-audit/probe_font_storage.py`。

这些结果证明存在可量化的应用数据压缩机会，进一步说明162B不是最终极限。但980/1271B都**尚未扣除新解码器、调用适配、对齐和状态成本**，不是已经多出来的可执行区。现有黑字还调用原生`TEXT`，直接替换字体格式会导致不兼容；必须先核查全部原生引用，再只在已验证应用层适配并验证全部页面像素。此实验没有改1.5.5字库、没有生成压缩版固件，更没有改底层驱动。

本机已有提醒从Flash读取4000B黑层和4000B红层到同一帧缓冲、核对CRC再刷新。因此关键基础已经存在。轮播不需要“张数×8000B”的RAM；应复用8000B画面缓冲、小读写缓冲和现有Flash接口。图片日历可在读入当前图片后叠加右侧日期。

## 更新后的实施判断

**尚未证明放不下，也尚未证明安全放得下。** 下一步应先在隔离构建中量化以下成本，再选布局：

1. 把提醒/图库的分页读写、CRC、提交校验共用；保持提醒原协议和槽地址不变。
2. 测量应用渲染与字库布局的消重/紧凑存储收益，计入新解码代码和运行状态成本；字体、现有页面输出保持一致。
3. 增加相册所需最小协议、播放列表及相对定时，编译给出实际增量；现在没有可引用的“相册必需N字节”测量值。
4. 核实高Flash区所有权、擦除范围和提交中断恢复；首先2–4张。独立计时绕开日历“未校时不工作”的门槛，但不改底层定时/蓝牙驱动。

4.2可借鉴其流程分层和分块读取；不照搬728KiB布局、45槽数组、频繁保存游标、授权机制或面板驱动。原样保留2.13启动、蓝牙初始化、面板、OTP/MAC/校准和堆栈边界。
