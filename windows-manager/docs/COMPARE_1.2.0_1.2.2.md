# 连接异常前后固件对比

2026-10-06。以升级前的 V1.2.0 对比 V1.2.1，以及只调整广播间隔的 V1.2.2。此次分析未修改生产固件、未刷设备。

## 结论

除了广播间隔，最重要的变化是 **两阶段全刷及其 BUSY 回调**。V1.2.2 保留了这组变化，因此把间隔改回约 1 秒，并没有恢复 V1.2.0 的刷新流程。

这组变化影响面板工作时间、BUSY 生命周期和进入休眠的时机，值得做单独回退对照；目前还不能认定它导致蓝牙连接失败。新固件冷启动的首张开机页通常没有触发额外清屏，不能用两阶段全刷解释所有连接失败。

## 实际镜像与源码核对

- 从留存源码独立重建 V1.2.0 和 V1.2.1，两份 APP 均与当时交付镜像逐字节一致。
- V1.2.0 APP SHA256：`838024e3175368c533fdfc576fd593297adb61ac48bba899102245358db754a5`。
- V1.2.1 APP SHA256：`c09c7a8fd92eea6776223cf8982dedcf82329d36aadae4688d09bfd5b773b527`。
- 原 APP 范围内（偏移 `0..0xddd3`）V1.2.0→V1.2.1 的 2880 个变化字节已全部归类，没有未解释的变化；追加运行区另外核对了源码、默认状态、辅助函数及重定位。
- 所有原生入口 BL 指令均实际解码，并核对其目标与对应版本的导出地址一致。
- V1.2.1→V1.2.2 原 APP 范围只有 7 个字节变化：广播间隔 2 字节，运行区复制长度 1 字节，两个重定位调用各 2 字节。另有开机版本图及随之移动的追加辅助区、固件 ID。

## 除间隔外的变化

| 部分 | V1.2.0 | V1.2.1 / V1.2.2 | 判断 |
| --- | --- | --- | --- |
| 全刷流程 | 将目标画面全刷一次 | 特定情况下先全刷白屏，BUSY 结束后重新初始化、装载目标、再全刷一次 | 最需要单独对照的行为变化 |
| BUSY 完成回调 | 保留硬件 BUSY 返回值；产品层只提交画面状态 | 产品层可返回 `1`，使原生回调继续等待第二阶段 | 影响忙状态、完成时间和休眠时机 |
| 时钟退出标记 | 没有专用清屏标记 | 时钟转月历时设置 `valid=3`，触发前述清屏 | 与切换画面路径相关 |
| 蓝牙名称后缀 | MAC 低三字节与前缀异或后，显示小写十六进制 | MAC 实际低三字节，显示大写 | 名称字符串变化；未改设备公开 MAC；长度保持不变 |
| 图标及版式 | 蓝牙图标 7×9；旧月历 | 图标 9×13；周标题色带、日期位置、农历月日等调整 | 显示变化，无新增广播控制 |
| 开机身份位置 | MAC 从 x=56 开始，电池 x=204 | MAC x=54，电池 x=206；版本更新 | 显示变化 |
| 编译布局 | 较小产品代码 | 产品代码增长，辅助区因版本图和代码大小重定位 | 未越过构建的静态内存边界 |

两阶段清屏仅在全刷且满足下列条件之一时触发：已发生快刷（`U->count` 非零）、时钟退出标记 `valid=3`、外部推送前仍保留时钟有效状态。并非所有刷新都增加第二阶段。分钟快刷算法、FAST/FLY 波形表本身未改变。

## 已排除的其他源码变化

实际辅助函数在消除 BL 地址重定位后，三版一致；默认策略前 28 字节一致（末 4 字节是不同版本的固件标识）。以下没有出现新的行为改动：

- 持续广播模式与定时接收窗口判断。
- 原生断线后重新启动广播路径。
- LED 输出高电平熄灯及每次唤醒时的引脚恢复。
- 面板复位低电平和稳定等待时间。
- BUSY 每阶段 225 次轮询上限与错误 4 的恢复逻辑。
- OTA 包校验、读回、最后提交及双槽写入机制。
- 自定义图片尺寸和缓冲区：250×122，两色平面各 4000 字节。
- 小字粗字体数据和原生 FAST/FLY 波形表。

没有发现新增的 40–56 秒停广播定时器。现有接收端观测到的静默，尚不能直接证明空中完全停止广播。

## 与本次实机现象的关系

91:A7 在线刷后、刷机线全拔、手机蓝牙关闭、管理端暂时停止的独立只读测试中：约 1.8–3.0 秒收到了该设备的可连接广播，信号约 -63 / -68 dBm；但全服务发现及只查 FF00 两种查询都返回 `Unreachable`，未建立可用 GATT 会话。

因此这次失败已经发生在收到广播之后，旧设备名称、8 秒内未扫描到设备、单独的 FF00 服务过滤均不能解释该次失败。尚未通过 GATT 读到线刷后的固件 ID；线刷 Verify 是用户报告通过。

两阶段清屏的命令序列测试曾通过，但用户仍看到新页面与旧时钟黑红像素混合，**光学问题仍未解决**。不能把 BUSY 完成当成无残影证明。

若连接问题仍能复现，可在保持约 1 秒间隔、MAC 命名及当前 UI 的前提下，仅回退两阶段清屏和 BUSY 返回值改动做对照。后续已观察到相同 V1.2.2 恢复通讯，见下文；不能据此认定两阶段刷新或广播间隔是连接根因。

## 后续验证：电脑蓝牙重启后，同一 V1.2.2 恢复

用户重启电脑蓝牙后报告 V1.2.2 通讯正常。随后管理端回执核实：

- 91:A7 读取状态成功，固件 ID 为 `28768807`，对应 V1.2.2。
- 同一设备的两次月历任务成功，进度 100%，刷新代次分别为 2、3，`busy=false`、`error=0`。
- 此次没有重新编译或刷入固件，间隔仍为 1022.5ms。暂不生成 687.5ms 回退包。
- 昨日 15:32 启动、监听 18766 的 V1.0.2 诊断后台已核对并停止，数据库完整备份。停前没有待执行任务或公告计划，不能断言它当时正在抢占蓝牙。18765 的 V1.2.2 管理端继续运行。

该结果反驳了“广播间隔一旦超过 1 秒就必然无法连接”的硬阈值解释，支持进一步检查电脑蓝牙栈或连接会话状态。由于旧后台停止与电脑蓝牙重启相近，尚不能将恢复唯一归因于其中一项。仅 91:A7 已有这次恢复的实际回执，不代表其余三块已验证或升级。

对“每秒重建广播”的额外核对：

1. 执行实际原生 `0x07fc25c0` 定时器入口，在正常启用、无校正的分支到达 `app_easy_timer` 时，参数为 6000，回调地址为 `0x07fc25c1`。SDK 定时单位为 10ms，即 60 秒。`0x2620` 的 `r7` 来自分钟字段，不是秒计数，不能用计满 59 推出每秒回调。
2. `0x07fc6af0` 的入口先检查 `adv_state`；已广播时直接返回。执行实际指令重复调用 100 次，没有进入 activity 分配函数 `0x07fc27a0`。因此每次调用不等于每次重建 activity。
3. 当前 `helpers.s` 窗口非零分支在乘以 100 后明确执行 `ldr r1, =0x07fc277d`。已有实际 Thumb 测试也核对 40 秒窗口输出 `r0=4000`、`r1=0x07fc277d`，不是把 100 当回调指针。
4. `adv_tick` 还只在秒字段为零时计数；未证实 99 命令的单位错误，当前分钟单位文档保持不变。

执行记录：`build/diagnostics/native-timer-adv-guard.json`。定时单位参考：[Renesas SDK6 定时器教程](https://lpccs-docs.renesas.com/Tutorial_SDK6/timer.html)。软件执行不模拟真实空口，以上指令证据用于核对机制，不替代长期连接及电流测试。

月历任务的 `optical_result_verified=false`，因此通讯恢复和 BUSY 完成仍不能证明残影消失；残影继续作为独立面板问题处理。

### V1.2.1 的恢复也已核实

用户随后报告 V1.2.1 同样恢复通讯。管理端核实 86:66 固件 ID 为 `90559ec8`（V1.2.1，广播间隔 2000ms），读取状态与月历任务均成功，`busy=false`、`error=0`。同时 91:A7 的 V1.2.2 保持成功回执。本轮没有刷入或修改任何固件。

这说明 2000ms 和 1022.5ms 均能在当前环境建立通讯，间隔超过 1000ms 不是此前故障的充分解释。保留现有间隔，优先检查电脑端蓝牙连接状态；现有证据仍不足以区分蓝牙栈、适配器、旧后台或多客户端会话的具体影响。83、BF 此时尚无新的状态回读，不将它们计入本次恢复验证。

证据：`build/diagnostics/radio121-122-after-host-bt-reset.json`。
