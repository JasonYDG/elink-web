# 第一张图库保存失败：4.2 寸实现对比与 1.5.8 修复

## 已确认的现场事实

两次失败任务分别开始于 2026-10-18 21:33:28 和 21:34:43，最后进度均为第一张图片 `8000/8000`。普通图片日历此前已成功上传并读回；故障发生在接收完成后的图库保存阶段，不是第一包像素发送失败。

Windows 返回 `0x800704C7`（十进制 -2147023673）。管理端原样显示系统的“操作已被用户取消”，不能据此认定用户点击了取消。下一次任务读到显示代次回到 1、校时状态丢失，符合设备重启迹象；没有读取复位原因寄存器，不能确定为看门狗或供电复位。

## 直接核对的 4.2 固件

样本是 `F:/AI/4.2-Elink/reference/epd42/originals/OM6626Full-261008.bin`，238532B，SHA256 `6fcedbb08bc39361a29b15e3ad22cbdd9d5907ed7f54b15d9405c5a2f81bd7ca`。本轮重新从同哈希 BIN 解码实际 Thumb 指令，没有以 APK 文案替代实现证据，也没有修改它的加密、授权或固件。

| 阶段 | 原固件位置 | 观察到的实现 |
|---|---|---|
| 开始保存 | `0x00425A10` | 检查槽号及图像参数，计算槽地址，调用擦除回调，初始化接收长度和 CRC16 |
| 接收数据 | `0x00425BD4` | 对本次输入累计 CRC16，把数据填入 256B 缓冲区；满页调用写入函数 |
| 写一页 | `0x004223F8` | 将不足部分填 FF，调用 256B 写回调，地址增加 256，清空缓冲计数 |
| 完成保存 | `0x00425FA8` | 刷出尾页，将字节数、CRC、有效状态放入槽元数据，然后保存元数据 |
| 外部图库 | `0x00426280`、`0x00422438` | 同样使用 256B 缓冲；检测新 4KiB 扇区并调用擦除回调 |
| 轮播 | `0x00425894` | 消费分钟事件，按间隔或星期映射选有效槽，由主流程显示 |

其开始阶段仍存在整槽擦除回调；当前证据不能证明全部擦写都是异步或永不阻塞。其元数据写入也不能直接等同于掉电原子提交。值得采用的是按接收进度分批落盘和增量校验，而不是复制对方地址或驱动。

另外实际执行了样本的接收、页缓冲与 memcpy 原指令，仅替换存储硬件回调：输入32个250B数据包，得到31个完整256B页和64B尾部；结束补齐最后一页192B FF，总像素及CRC16与输入一致，每个接收包最多触发一次页写。脚本 `verify_om6626_buffer.py` 可复跑。这验证分批落盘的代码行为，不代表已测对方实体芯片速度。

4.2 的内部图库预算常量是 `0xB6000`，按 4096B 对齐计算槽大小，并限制最多 45 槽；这个预算已大于我们整颗 512KiB Flash。两块板的芯片、代码布局和图库容量不同，不能用它支持更多功能来推定 DA14585 的固定代码段必然足够。

## 1.5.7 的问题与 1.5.8 的改法

1.5.7 的 `BD02` 一次完成：RAM CRC32 → 擦除 8192B → 编程 8000B → 读回 8000B CRC32。该命令返回前无法回到正常应用事件处理；播放列表提交又重复读回全部图片。实机故障点与这条长路径吻合。此前 NOR 仿真验证了内容和地址，但把驱动调用视为立即完成，未覆盖真实擦写阻塞时长，这是原验证的缺口。

1.5.8 把每张图的保存拆成 32 次请求，每次 250B（正好整除两个 4000B 色层）。沿用原生页编程 helper，一次最多两次页编程；第 0、16 步分别擦除一个 4096B 扇区。每步读回 250B，累计 CRC32，整张 CRC 相符才增加暂存数量。步号必须连续，重复、乱序和未完成图片均不能提交。主机每步核对状态和步号，显示“保存第几张、第几块”。

提交阶段保留双配置页、序号、CRC 及最后写 ready 的原子提交，不再重复同步扫描整组图片。每张图片显示前仍独立读回并核对 CRC。新图库只写非活动图像区，失败不替换已提交的旧播放列表；可以重新开始暂存事务。该改动保证每次图片保存请求的工作量有界，实际耗时仍须实体 Flash 测量。

新图库状态协议为 ELA1 版本 2，`BD02` 增加 0–31 步号。新管理端在写入前拒绝 1.5.7 的旧图库协议，提示升级；原单图、时钟、日历、提醒与 OTA 命令保持兼容。新的停止轮播命令仍可停止旧版图库。不要用旧管理端保存新版图库。

Windows 中止读写会显示传输阶段和错误码，不再把系统文案当作用户取消。图库保存步骤失败后停止本次任务，不自动重复擦写；提交发出后仍使用“结果待核对”状态。
