用户随后将主要体验问题明确为“能连接，但操作时容易断开或反复重连”。因此实施优先级先调整为连接会话短时复用、主动/意外断开区分及有界恢复，再推进大包与模板。具体源码和历史任务证据见 [蓝牙交互专项复核](BLE_INTERACTION_REVIEW.md)；本计划中的相册与存储前提不变。

## 第一阶段：蓝牙可观察性与大包传图

复用 [WORKITEMS_POWER.md](WORKITEMS_POWER.md) 的 WI-5，不新增重复工作项。

1. 在后端记录连接、能力查询、像素传输、提交和 BUSY 完成各阶段耗时；显示固件 ID、实际包长、已确认字节数与结果类型。稳定性先用数据评估。
2. 为新接收能力增加明确声明；旧设备默认17B。固件和客户端同时支持17/64/128B像素块，保留写入带响应与严格顺序。
3. 计算值容量时区分 ATT MTU、特征可写容量与3B业务头；不把任意接口返回的244直接当作所有平台的ATT MTU。当前OTA能收136B不能替代图片接收分支的长度检查。
4. 原有偏移、校验和、提交前状态、提交后显示代次、190秒两段刷新等待和 `delivery_unknown` 语义不变。新包长下进度按累计字节更新，不能继续固定乘17。

## 第二阶段：模板与照片渲染在管理端完成

保持设备读取固定像素帧。250×122逻辑画布在本固件对应122×250原生布局，每层4000B，共8000B。

模板包建议具有格式版本、画布、模板描述、资源及校验清单。导入先验证版本、尺寸、资源大小和内容，再保存为新模板；不悄悄覆盖已有同名模板。包内路径必须限制在包内，不允许越界文件写入。沿用同一个渲染器生成预览、PNG、帧和哈希。

首轮仅扩展用户实际需要的字号、位置、颜色、日期/时间占位符及照片裁切。为照片提供阈值和一种可关闭的误差扩散，保留原有文字模板的清晰边缘。暂不移植完整多色/多灰阶算法；250×122黑白红屏不能通过软件选项自然变为另一种物理面板。

验收：导出后重新导入，静态模板使用相同输入时帧字节一致；动态日期字段在相同冻结时间下比较。缺资源、错误尺寸、畸形包被拒绝；已有模板/任务快照和数据目录迁移不受影响。

## 第三阶段：先核实可用 Flash 和执行代码空间

沿用 [WORKITEMS_FONT.md](WORKITEMS_FONT.md) 的 FW-8：核对实际Flash型号/容量、完整只读备份、擦除粒度与现存数据。512KiB导出及完整分块日志已归档，高256KiB本次全FF；物理容量和地址用途仍需核对，不能直接认定可写。保留原件和备份哈希，不进行整片擦除。

已有固定布局必须保留：两应用区起点0x2000/0x14000；提醒区 `[0x26000,0x36000)`；产品区0x38000；屏幕配置0x39000/0x3A000。本文没有分配新的Flash写入地址。

候选包当前固定执行区的剩余字节：`.product`32、`.reminder_extra`68、`.reminder`512、`.clock`432。这些区段不连续，不能当作一个总空间直接使用。先重新规划链接区域、验证与原生代码/字库/状态没有重叠，再增加相册。DA14585不是从任意外部Flash地址直接执行新增代码；也不要为多图在96KiB RAM中分配多份完整帧，应复用既有8000B画面缓冲和小块读缓冲。

预算示例仅用于说明：若最终证明高256KiB可全用于图库，先扣两页4KiB的元数据日志和一个8KiB更新备用槽，剩余理论上可容纳30个8KiB照片槽。**这不是当前已证实的容量**。首轮只开放2–4张，确认兼容后再根据实际存储表公布上限；不要减少现有7条待提醒额度来制造相册空间。

验收：存储区间互不重叠；构建对每个边界有断言；原有提醒和产品/面板数据逐字节保留；执行代码满足Cortex-M0指令集和链接边界；掉电样本不把半张图片识别为有效槽。

## 第四阶段：独立图库和播放策略

建议先实现按顺序循环。存储模型与接口分开：

| 对象 | 最小必要字段 |
|---|---|
| 图片槽 | 格式版本、slot、token/内容ID、宽高、原生像素格式、长度、CRC32、状态、短备注 |
| 播放策略 | enabled、有效槽有序列表、间隔、重启恢复策略、配置代次、校验 |
| 运行状态 | 当前/待显示槽、已完成代次、busy、错误、下一次相对到期时间 |

设备接口需要覆盖能力查询、列槽、开始上传、带偏移写入、校验提交、终止、显示槽、删除槽、读取/保存播放策略。命令号和能力位在完整核对现有分发器后分配，本文不假定未使用编号就一定安全。

上传过程：写入未启用槽 → 分页写像素 → CRC与全量读回 → 最后提交有效状态 → 返回可查询结果。可分开选择“仅保存”和“保存后显示”。编辑图片先写备用槽，校验成功后再更新播放列表，最后回收旧槽；坏图、半图和被删除的槽不参与播放。

元数据采用带代次和CRC的双副本或追加日志，显式定义最后提交点。用户改配置或列表时才写持久化策略；正常轮播游标优先留在保留RAM，冷启动可以从第一张恢复，避免每分钟重写同一元数据扇区。若用户要求记住准确播放位置，再另行设计低频检查点和磨损预算。

按最新需求改为小时至天级：默认评估每天换图，提供1/2/3/6/12小时、1/2天及自定义小时。实际刷新策略、每次是否含清屏及电池消耗需实测，不据此承诺续航。首轮不引入随机、星期映射、跨多个图库或照片压缩，避免掩盖基础可靠性问题。

## 第五阶段：显示仲裁与不依赖电脑的执行

建议优先关系：OTA/当前传输或刷新互斥 → 已到期提醒 → 用户主动显示 → 相册后台轮播 → 默认时钟/日历。相册开启是明确的页面所有权，时钟分钟回调不应抢回页面。

提醒打断相册时暂停推进；提醒持续时间结束后按保存的播放策略恢复。用户主动切到日历/时钟/静态照片时，应明确停止相册或选择恢复策略；管理端公告计划不能与设备相册互相覆盖。BUSY未结束时合并到一次待切换，不累积一串过期刷新；成功完成后再更新已显示槽与代次。

当前 `product_clock()` 在 `!time_valid()` 时返回，所以不能只把相册 tick 放到后面。相对轮播应允许在没有准确日历时间时运行；先验证原生节拍是否在未校时状态触发，否则采用可休眠的相对定时器。提醒仍要求正确校时。完全掉电后照片和策略可保留，但播放游标、计时与RTC分别定义恢复方式，不能笼统承诺全状态恢复。

BUSY超时、CRC错误或槽失效时保留错误，不把一次失败记为完成；避免连续高速重刷同一张坏图。具体恢复次数和是否暂停在实测后固定，不引入无限自动重试。

验收至少包含：关闭电脑且断开蓝牙后连续轮播；提醒抢占及恢复；传图和OTA期间不切图；编辑/删除当前槽；上传中断与提交点掉电；全断电后恢复；相同图不无故重复全刷；24小时稳定性、真实画面和电流。蓝牙写入成功、模拟像素和Flash读回不等于光学完成。
