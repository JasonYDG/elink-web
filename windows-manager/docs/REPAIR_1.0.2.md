# 1.0.2 刷新期间休眠与开机页重复绘制修复

适用 DA14585 五测试点、2.13 寸黑白红、250×122 标签。本版延续 1.0.1 的内存布局与 ELK1 协议。

## 实际观察

1.0.1 已通过有线 Verify，用户看到 ELINK 开机页。随后用户报告开机页反复刷新、LED 交替亮灭，以及推送模板后整屏红黑混合花屏。

本机 75 秒被动扫描记录到 `ELINK-BWR-732dfd` / `18:BC:5A:6B:91:A7`。独立 BLE 连接获得 FF00 服务与 32 字节状态，固件标识为 `d25ce8b0`，默认每分钟广播 30 秒。管理端模板传输完成，设备 BUSY 结束、刷新代次变化，但用户观察到花屏。因此“传输成功”不能作为“屏幕正常”的证据。

证据保存在工作区 `build/diagnostics/ble-after-1.0.1-flash.json`、`physical-1.0.1-status.json` 与管理端任务回执中。1.0.1 交付文件未被覆盖。

## 修复依据

刷新尾部的自定义代码在 `sleep_md != 0` 时把 `sleep_pend` 写成 0。Renesas SDK 的 `arch_disable_sleep()` 在相同条件下写入 `0x80 | ARCH_SLEEP_OFF`，原生二维码刷新尾部也写入 0x80。0 表示没有待处理请求，会在恢复睡眠控制时丢失“暂停休眠”的要求。模板刷新发生在 BLE 写事件中，正好经过这一分支。

1.0.2 将该字节改为 0x80，使刷新期间暂停休眠的请求能被原生流程执行；BUSY 完成后的原生睡眠恢复流程保留。新增测试执行真正构建的 Thumb 指令，从 BLE 睡眠阻塞状态完成 8000 字节提交，检查实际 `sleep_pend` 与 BUSY。

原生未校时时的分钟定时器与广播结束回调会反复调用开机绘图。1.0.2 在开机绘图入口检查校时标志、BUSY 和刷新代次：首次显示后不再重画开机页，仍继续运行计时和蓝牙广播。校时标志也避免长期运行时 16 位代次回绕又进入开机页。新增测试完成一次开机全刷后再次执行原生开机入口，检查没有新增屏幕命令或代次变化，并覆盖代次回绕。

两个测试在旧代码上均失败，修复后全部 20 项回归测试通过。证据：`build/diagnostics/sleep-and-repeat-regression-before.log`、`sleep-and-repeat-regression-after.log`、`build/tests-1.0.2.log`。测试替代了射频、供电和墨水屏 BUSY 边界，实际显示效果还需在标签上确认。

## 升级与无按键使用

运行 1.0.1 的标签可以选择 `firmware/elink-bwr-1.0.2.elink-update.json` 做蓝牙 OTA，后台先检查 MTU，逐块写入、完整读回，提交后重连核对标识 `4ef1e075`。首次安装、从 1.0.0 恢复或 OTA 容量检查不通过时，使用 `firmware/elink-bwr-1.0.2-spi.bin` 有线刷入，偏移 0。不要把应用镜像写到 SPI 偏移 0，不要操作 OTP。

没有按键无需禁止休眠。默认每分钟开放 30 秒接收窗口；后台按已登记地址等待窗口，连接后执行任务。接收间隔和屏幕更新间隔分别配置，静态内容不会因蓝牙唤醒而重画。断电后回到默认接收设置，可重新连接恢复后台配置。见 `CONNECTION.md`。

完整 SPI 为 241664 字节，应用为 60084 字节。哈希和状态布局以 `firmware/manifest.json` 为准。软件修复不替代三色显示、LED、电流和长期连续连接的实机验收。

管理端任务记录改为保留每条任务的 DOM，仅更新变化字段，展开的回执不会在轮询时收起。新增“实时更新”开关与“刷新记录”按钮，可暂停日志更新阅读，后台设备操作不受影响。

## 实机 OTA 后的管理端修订 r2

2026-10-05，本机通过蓝牙写入本版，全部应用字节读回一致。提交复位时 WinRT 的未完成 ATT 写返回 `OSError / WinError -2147023673`，初版管理端漏接此异常，提前标为“结果待核对”。随后用独立连接读取到 `4ef1e075`、ELK1 协议正常、BUSY 已结束，证明新版本已经启动；没有重复擦写。

r2 管理端在提交复位时遇到这类 Windows 接口错误，会继续执行重连与新版本标识核对。仍然只有实际读到目标标识才能报告升级成功；中途写入或读回失败不提交，新版本无法确认时仍保留“结果待核对”。后台回归测试加入真实复位对应的 OSError 取消路径。r2 还在连接成功时清除上次等待广播的旧错误提示。

r2 的固件文件与初版 1.0.2 完全一致。已读到 `4ef1e075` 的标签不必重新刷入；使用配套 r2 管理端即可。最终交付路径以 `CURRENT_DELIVERY.json` 为准。
