# 1.5.22：日历中午额外重绘

用户询问先前“要求午夜更新，实际中午刷新”的问题在当前固件和网页中是否仍存在。本次直接核对当前发布的1.5.21/feacec0e与Web1.1.21，并执行原生0x07fc25c0分钟入口，未连接设备或使用Computer Use。

## 发现与修正

1.5.21确实会在中午额外重绘。原生分钟回调在11:59→12:00和23:59→00:00都向应用传入0x80，正常分钟传2。0x80用于旧时钟AM/PM变化，并非专门的换日事件。应用把它同时当作静态日历强制重绘标记，绕过了“日期没有改变则返回”的判断。原生公历日期本身在午夜推进，没有发现整天日期提前12小时。

旧镜像仿真：11:59→12:00时日期仍为11月14日，但显示代次从1变2；23:59→00:00时日期推进到11月15日，也刷新。新增原生回调回归在旧镜像失败，见backup/2026-11-14/midnight-calendar-audit/noon-red.txt及native-trace.txt。过去直接设置新日期的UI测试覆盖不到原生中午0x80这一调用方式，不能代替此检查。

1.5.22先判断日历模式的日期与视图缓存。原生0x80不再绕过该判断；明确的手动切页/重绘请求额外使用应用内部0x100标记。这样月历、单图图片日历及离线图片日历的自动刷新按日期变化进行，手动重绘与同一天更换图片仍然生效。协议9C、UI状态大小、时钟分钟差分、全刷维护、时区规则及原生计时器保持。

## 网页时间设置

Web1.1.21现有校时逻辑正确：本地时间使用getHours()的0..23；荷兰时间明确hourCycle=h23。午夜下发hour=0，中午下发hour=12。新加坡本地及荷兰冬/夏令时的20份普通/安静校时包均通过检查，新增Node回归固定时区验证，避免随运行电脑时区而变化。

时间与时区由时钟、月历和图片日历共用。默认local随手机/电脑本地时区；选择Europe/Amsterdam后按荷兰日期跨日。网页没有“每天中午刷新日历”的独立设置，时钟5/15/60分钟更新频率也不改变日历跨日判断。新版网页把共用范围写入时间选择标签和说明，更新在线固件入口；校时算法未修改。实际浏览器已存设置、实际安装版本和真机时间本次没有读取，不能声称用户设备已自动完成升级或校时。

## 验证范围

执行真实分钟入口核对月历/图片日历中午不刷、午夜刷一次；月末、年末、2024年2月28/29闰日边界；午夜忙碌后下一分钟补刷，包含时钟间隔设为60分钟的情况；同日手动重绘与更换照片；左侧原图保持。SPI、BUSY、ROM服务和诊断日志为模拟边界，日期/小时推进、原生传参、应用判断和像素绘制执行编译指令。

rollover-audit/index.html中的8张PNG均250×122，来自交付应用的真实模拟RAM。两种日历在中午显示代次不变，午夜递增1。例子保留原生秒相位37，所以实际执行到00:00:37；日历在跨日后的分钟回调更新，不把它宣传为硬件精确00:00:00唤醒。

与1.5.21的全部应用字节比较，差异仅允许既有应用clock/product/reminder段及其明确的应用调用/只读引用重定位、版本与固件ID。字库、笔画遮罩算法、启动、原生计时/驱动/波形、无线、身份、校准、Flash与堆栈边界保持。标准9页预览重新从1.5.22导出；1.5.21的24节气/90字审计可继续参考，字库资产逐字节相同，未把旧图的固件来源改成新版。

## 快刷实屏反馈与原生配置恢复

同轮用户补充：快刷1数字正常但四周严重黑框，快刷2变化笔画太浅；用户随后确认实测版本为1.5.21；本次未通过蓝牙读回。检查应用发现它在原生初始化后又写0x3C=0，并通过0x0F=9、0x01=102缩短扫描。实际执行原生初始化的回归显示边框原值5，应用最后覆盖成0；此回归先失败，撤销覆盖后通过两种模式。上游原生初始化依据：https://github.com/tpunix/HMCLOCK/blob/master/src/epd/epd.c 。

最终1.5.22撤销上述三项应用层覆盖，笔画R层遮罩保留，扫描与边框由未改动的原生初始化负责。恢复原配置是对已定位软件问题的修正；它是否消除黑框、提高第二种发色深度仍须实屏复验，不能由模拟RAM或SPI字节证明。未增加脉冲、提高电压或修改波形表。新Web设置默认全刷，两种快刷标为实验重测，既有设置保持，需要用户主动改为全刷。旧黑框可先从时钟切到默认页，走既有白清屏/目标流程。
